AgentFlow 项目 → 面试考点讲稿

把你的项目翻译成面试官听得懂的证据 · 每个考点给出「代码位置 + 一句话讲法 + 追问预判」

30 秒项目介绍（背下来）

"我做了一个本地的 Agent 编排平台。前端用 React Flow 拖拽定义执行拓扑，后端用 FastAPI + SQLite。核心是一个可切换的执行引擎：手写的 Agent Loop 做线性流程，LangGraph 做有条件分支、有界循环和断点续跑。工具层支持 Function Calling、HTTP 工具、MCP stdio 客户端和 BM25 知识库。运行环境有 MAX_STEPS 防死循环、HITL 人工审批、指数退避重试和幂等缓存，全链路 SSE 事件流做可观测和回放。"

这段话覆盖了 6 个强覆盖考点，且每一句都能被追问到具体代码——这就是它比"我调了个 LangChain"强的地方。

一、强覆盖 · 直接能讲（6 项）

工具调用 / MCP

覆盖 95

项目对应：llm.py:218-256（FC 参数分片累积）、loop.py:511-586（错误回灌）、tool_runner.py（校验/重试/幂等/白名单）、mcp_client.py（stdio + JSON-RPC）

  • Function Calling 的 arguments 是分片来的，按 index 累积、整轮结束一次组装——不这样上层就要自己写拼装状态机。
  • FC 工具失败不让 run 挂掉，把错误当 tool 消息回给模型改参数重试；tool 节点失败则让 run 失败。两种失败语义是刻意区分的。
  • 重试只对连接错误/超时/5xx，4xx 是参数问题重试只会重复挨骂；指数退避封顶 1s。
  • resolve_by_name 只认绑定的工具，模型调未绑定工具直接 TOOL_NOT_BOUND——这就是工具幻觉防护。
  • MCP 用同步 Popen + 线程，因为 Windows SelectorEventLoop 不支持 create_subprocess_exec。
一句话讲法："FC 只是模型发意图，执行权在我这侧。我把校验、重试、幂等、白名单都放在执行器里，模型失败时能拿到结构化错误自我修正。"
预判追问：参数格式不对怎么办？→ JSON 解析失败回 ERROR: 参数不是合法 JSON 给模型，最多 2 轮。MCP 和 FC 区别？→ MCP 是连接协议，底层仍走 FC 触发。怎么防越权？→ 工具白名单 + human 节点审批（原型不做沙箱）。

系统设计

覆盖 90

项目对应：整个仓库就是答案——接入层 app/api/、对话管理 state + checkpointer、Agent 核心 loop.py + graph_runner.py、工具层 tool/mcp/knowledge、输出管控 event_bus + _fail()

一句话讲法："我按五层设计：接入、对话管理、Agent 核心、工具、输出管控。关键取舍是把事件协议做成引擎无关——三个 runner 共用同一套事件，前端不用知道谁在跑。"
预判追问：成本怎么控？→ token 精确 usage 校准 + 节点级 max_tokens + 子流程 token 累加到父 run + 评测页的"每次成功成本"软门禁。

架构模式

覆盖 85

项目对应：loop.py（手写 ReAct）、graph_runner.py（LangGraph）、README 里三引擎对照表

  • 手写 Loop 只能按拓扑序线性跑；condition 会把两条分支都跑一遍、loop 回不去上游——这正是换 LangGraph 的动机，面试讲"为什么用图不用链"的现成案例。
  • ReAct 循环在 _run_llm_node：一次模型调用算一步，FC 多轮逐轮计数，防"工具喂结果→无限追问"。
一句话讲法："我没上来就用框架，先手写 Loop 跑通，遇到条件分支和回边才换 LangGraph，保留了 loop runner 做对照。"
预判追问：Agent vs Workflow？→ 我的 tool 节点是 Workflow（写死的调用），llm 节点绑工具是 Agent（模型决定）。一个项目里两种都有，按场景切。

Harness 与运行时

覆盖 852026 重灾区

项目对应：graph_runner.py:290-312, 413-444（HumanPause + checkpointer）、loop.py:153-170, 655（state 快照续跑）、subflow.py（子流程内联）

  • 官方 interrupt() 在 Python 3.10 上不可用（contextvar 进不去异步节点），改用"抛异常暂停 + aupdate_state 后 ainvoke(None) 续跑"，checkpoint 仍在，语义一样是真中断。
  • 续跑时 LangGraph 会从头重跑被中断节点，所以显式传 resume_node 标记，否则重复发一次 node_started。
  • 子流程用 MemorySaver 单独编译图、不落 run 不发事件，token/cost 累加进父 run，父子各自受 MAX_STEPS 约束。
一句话讲法："HITL 触发时把状态写进 checkpoint，Loop 挂在等待态；审批通过 aupdate_state 灌回，再 ainvoke(None) 从断点继续。"
预判追问：状态快照怎么实现？→ thread_id=run_id + AsyncSqliteSaver，每 superstep 落盘。为什么不用官方 interrupt？→ 上面那段 Python 3.10 的坑，讲出来很加分。

LLM 基础

二、中覆盖 · 能讲但有缺口（1 项）

评估与安全

覆盖 65

已具备：全链路 SSE 事件留存 + 运行回放（可观测性）、工具调用记录、结构化错误码体系、human 节点审批高危操作、AST 白名单防 eval 注入、API Key 脱敏展示

缺口：

  • 评测页 EvalPage.tsx 目前是前端原型（pass^3、硬/软门禁、异模型 Judge 的框架有了），后端评测 API 未接——README 里标为 R6。
  • 没有 Prompt Injection / 间接注入的防御（数据指令分离）。
  • 没有幻觉率量化、没有沙箱（tool_runner.py 注释明确说原型不做，靠 human 审批兜底）。
讲法："可观测性我做完了：事件流 + 回放 + 工具调用记录。评测体系框架已设计好（pass^3、异模型 Judge、硬软门禁），正在接后端 API。"——诚实说明进度，反而显得靠谱。

三、弱覆盖 · 不建议硬讲（2 项）

记忆与上下文工程

覆盖 40

有：短期 state、BM25 + MMR 检索（RAG 的一半）。缺：向量检索（README 明说当前是 BM25 关键词）、长期记忆持久化、滑动窗口 + 摘要压缩、Lost in the Middle 缓解。

低成本补齐（约 1 天）：在 build_messages() 里加滑动窗口 + 把滚出的历史压成结构化摘要写回 variables——补齐后这个考点立刻从 40 到 75，且代码改动很小。

多智能体

覆盖 45

有：子流程内联是主-子 Agent 的雏形。缺：Agent 间通信协议、隔离、失败回退。图引擎注释里还坦承"同一节点多条普通出边会 fan-out，两条分支共享 data 字典，互相覆盖风险由使用方承担"。

讲法：不要说"我做了多智能体"，要说"我做了子流程隔离和 token 归并，多 Agent 通信和状态隔离是我下一步要解决的"。把已知取舍讲出来，比硬吹更得分。

四、真正的金矿：5 个"取舍与踩坑"

面试官追问"你们项目里具体怎么做的"时，下面这些比背概念值钱十倍——它们证明你真的写过、踩过、想过。

坑 / 取舍你的解法对应的加分答法
Windows SelectorEventLoop 不支持子进程Popen + asyncio.to_thread运行时工程要适配平台，不是照抄文档
官方 interrupt() 在 Python 3.10 不可用抛异常暂停 + checkpoint 续跑HITL 状态机怎么暂停恢复
FC 错误 vs tool 节点错误两种语义前者回灌模型、后者让 run 失败"错误当观察" vs "用户没有模型替他重试"
幂等的边界同工具+同参数 TTL 内复用；业务幂等键留给业务原型层证明"不重复下单"就够了，讲清边界
节点级 model 覆盖系统默认错误里带"实际请求哪个模型 / 怎么改"的可读提示可观测性不只是 Trace，还有可诊断的错误文案
