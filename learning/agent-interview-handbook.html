主题 1 · 基础概念与架构模式

基础 用大白话说清什么是 Agent？它和 Workflow、传统对话系统的边界在哪？
  • 一句话内核：Agent = 以 LLM 为大脑，能自主决定"下一步做什么"的系统。四大能力：规划、工具使用、记忆、根据环境反馈循环迭代。
  • 和 Workflow 的区别：Workflow 的路径是人预先写死的（固定 if-else / DAG），步骤确定；Agent 的路径是模型在运行时动态决定的，同样输入可能走不同步骤。
  • 和 Siri 类助手的区别：传统助手是"意图识别 → 调用固定技能"，没有自主规划、反思和多步拆解，不算强 Agent。
  • 为什么用 Agent：当任务步骤无法预先穷举、需要根据中间结果动态调整时，用灵活性换确定性。
加分答法：引用 Anthropic《Building effective agents》的原则——"能用 Workflow 解决的就别上 Agent"，因为 Agent 用延迟、成本和不确定性换灵活性。然后给选型判断：任务步骤能否预先穷举？对延迟/成本是否敏感？容错要求高不高？
必被追问：你们项目里哪些环节用 Workflow、哪些用 Agent？为什么这么切分？——提前准备好你项目里的具体例子。
基础 最小可用 Agent 的核心模块是不是一个 ReAct Loop？除了工具调用还必须实现什么？
  • ReAct Loop 是核心骨架：Thought → Action → Observation 循环。
  • 但要真正可用，至少还要：① 终止条件（最终答案 / 最大步数 / 超时）；② 状态管理（消息历史、上下文）；③ 工具执行与结果回灌；④ 异常处理（工具报错、格式错误、重复调用）。
  • 生产级还要加：记忆层、权限控制、可观测性（Trace）。
加分答法：把 Loop 画成一个状态机：思考态 → 调用态 → 观察态 → （继续或终止），并说明每一态如何暂停/恢复——这正好引出 Harness 的概念。
基础 ReAct 是什么？工作流程和优缺点分别是什么？
  • 原理：Reasoning + Acting 交替。每步：Thought（推理现状、拆解下一步）→ Action（按格式调用工具）→ Observation（拿到结果）→ 循环，直到 Thought 得出 Final Answer。
  • 优点：有思考链可解释；能利用外部工具弥补模型知识/能力边界；能根据观察动态调整。
  • 缺点：步数多、Token 消耗大；可能死循环；受上下文窗口限制；思考链错误会传播。
加分答法：主动说出防死循环三件套：最大步数硬限制、重复动作检测（工具名+参数哈希）、超时控制。
进阶 ReAct 和 Plan-Execute-Replan 的区别？分别适合什么场景？复杂场景怎么兼顾？
  • ReAct：边想边做，每步都推理，适应动态环境；但全局规划弱、容易目标漂移。
  • Plan-Execute-Replan：先出完整计划 → 逐步执行 → 遇偏差重新规划。长任务更稳、步骤可并行、进度可控；但需要额外"监管 Agent"判断何时 replan。
  • 场景：短任务、工具交互密集 → ReAct；长程任务、可并行、需进度可观测 → Plan-Execute。
  • 兼顾：外层用 Plan-Execute 做全局编排，内层每个子任务用 ReAct 处理动态交互——分层混合架构。
加分答法：指出"为什么需要监管 Agent"：执行 Agent 自己判断"我跑偏了"是不可靠的，需要一个独立视角对照初始目标评估偏差，避免既当运动员又当裁判。
进阶 Agent 项目与传统后端项目的架构差异体现在哪？
  • 控制流从"代码写死"变成"模型运行时决定"，执行路径不确定。
  • 状态从 DB/缓存变成"对话上下文 + 工具结果 + 记忆"多层结构。
  • 新增"提示词/上下文"这一层需要版本管理和 A/B 测试。
  • 可靠性从"确定性测试"变成"概率性评估"：需要轨迹评测、Golden Dataset、LLM-as-Judge。
  • 新增成本和延迟作为一等公民：Token、步数、模型选择都要监控。

主题 2 · Agent Harness 与运行时工程 2026 新增

这一节是 2026 年才真正热起来的方向，很多概念半年前还不存在，考的是理解设计动机，不是背定义。
高压 Prompt Engineering、Context Engineering、Harness Engineering 三者有什么区别？
  • Prompt Engineering：优化单条指令的措辞、结构、示例，让模型更懂你要什么。
  • Context Engineering：设计"喂给模型什么信息、以什么形式、在什么时候喂"——包括检索什么、压缩什么、工具结果怎么组织、历史怎么放。核心是上下文是有限资源，要精打细算。
  • Harness Engineering：设计整个运行环境——状态机、工具注册与权限、暂停/恢复、超时重试、可观测性、人工介入点。相当于给模型套的"车架"。
加分答法：用一句话串起来：Prompt 管"怎么说"，Context 管"给什么"，Harness 管"怎么跑"。Harness 火起来的原因是——大家发现 Agent 的瓶颈不在模型聪不聪明，而在运行时工程做不做得稳。
进阶 LangChain 和 LangGraph 有什么区别？LangGraph 的状态快照机制怎么实现？
  • LangChain：链式编排，适合线性/简单 DAG 流程，抽象高、上手快。
  • LangGraph：图编排，节点 + 边 + 状态，支持循环、条件分支、人工介入、断点续跑，适合有状态、多轮、需要精确控制的 Agent。
  • 状态快照（checkpoint）：每个节点执行后把当前 State（消息、变量、进度）持久化到 checkpointer（内存/Redis/DB），带上 thread_id。中断后凭 thread_id 恢复到最近一步继续执行。
加分答法：联系 HITL——人工确认触发时，Loop 处于"等待态"，状态被暂存；审批通过后从 checkpoint 恢复。这就是"状态暂停、暂存、恢复"的落地方式。
高压 Skill 的渐进式披露具体怎么实现？为什么能减少 Token 消耗？
  • 三层加载：① 元数据层——只常驻 name + description（几十 token）；② 指令层——命中后才加载完整 SKILL.md；③ 资源层——需要时才加载子脚本、参考文档。
  • 减少 Token：注册上百个 Skill 时，如果全部正文塞进上下文会爆炸；渐进式披露让模型先用少量元数据判断相关性，按需展开，上下文里始终只有当前任务需要的内容。
  • 实现：本质是一套"检索 + 按需挂载"的机制——描述做路由，正文做加载，脚本做执行。
加分答法：类比操作系统的"按需分页"——不是所有能力都常驻内存，用到才换入。这个比喻面试官很容易记住。
进阶 上百个候选 Skill 怎么处理——检索、分层还是渐进式披露？
  • 组合拳：先分层（按领域分组，先选组再选技能）→ 再用描述做向量/关键词检索召回 Top-K → 最后渐进式披露只加载命中项的正文。
  • 同时注意工具/Skill 描述要有区分度，避免语义重叠导致选错——大规模工具集下这是幻觉高发点。

主题 3 · 工具调用：Function Calling、MCP 与 Skills

基础 Function Calling 的原理是什么？模型如何知道该调用哪个工具？
  • 开发者用 JSON Schema 描述工具（name / description / parameters），随请求传给模型。
  • 模型本身不执行函数，只输出结构化的 tool_call（函数名 + 参数）；应用层解析、校验、执行真实函数，把结果作为 tool 消息回灌，模型再继续推理。
  • "知道调哪个"靠描述和参数的语义匹配——本质仍是生成，不是查表，所以会选错、会编造参数。
加分答法：点出"模型只负责发起意图，执行权在应用侧"——这是理解后面所有安全问题（越权、注入、沙箱）的前提。
进阶 大模型返回的 Function Call 参数格式不对，工程上怎么处理？
  • ① 用 JSON Schema 校验（如 Pydantic）；② 校验失败不要把异常直接抛给用户，而是把"错误信息 + 期望格式"作为观察回灌给模型，让它自我修正；③ 限制重试次数（如 2 次），仍失败则降级到默认参数或人工介入；④ 记录此类事件用于评估。
加分答法：强调"把错误当反馈而不是当异常"——这是 Agent 和系统的重要区别：错误是循环里的一种观察，可以用来纠错。
高频 MCP 是什么？它解决了什么问题？和 Function Calling 的区别？
  • MCP（Model Context Protocol）：开放协议，标准化"AI 应用 ↔ 外部工具/数据源"的连接方式，类比 AI 界的 USB-C。
  • 解决三大痛点：① 厂商绑定——各家 Function Calling 的Schema 不兼容，换模型要改代码；② 静态配置——新增工具要改代码、重启；③ 无执行标准——超时、错误、重试全靠自己硬编码。
  • 核心改进：一次开发，任意支持 MCP 的客户端可用；运行时动态发现工具；统一的通信与错误处理规范。
  • 和 Function Calling 的根本区别：Function Calling 是"模型的能力"（输出调用意图）；MCP 是"工具接入的协议标准"（工具怎么被发现、连接、通信）。MCP 底层通常仍走 Function Calling 触发。
  • 通信方式：stdio（本地进程）、SSE / Streamable HTTP（远程服务）。
加分答法：顺手理清协议分工：MCP 管工具连接，A2A 管 Agent 之间通信，AG-UI 管 Agent 与前端 UI 的事件流。这个分类 2026 年很爱考。
高频 MCP 和 Skills 有什么区别？Prompt / Skill / Subagent 分别怎么理解？
  • MCP：连接外部能力的"协议/管道"——解决能力从哪来、怎么连。
  • Skill：封装"怎么完成一类任务"的知识包（指令 + 脚本 + 资源），解决能力怎么用、流程是什么。
  • Prompt：给模型的即时指令；Subagent：独立上下文的子智能体，用于隔离和分工。
  • 一句话：MCP 是插座，Skill 是说明书，Subagent 是另一个工人。
进阶 大规模工具集下如何降低工具调用幻觉、提升选对工具的准确率？
  • 工具描述写得精准、有区分度，避免语义重叠；
  • 工具检索：先按语义召回 Top-K 候选，不把全部工具塞进上下文；
  • 分层与渐进披露；
  • 严格校验工具名白名单，不存在的工具直接拒绝并回灌错误；
  • 对高风险工具加二次确认。
进阶 工具调用报错、超时、连续失败时，重试与异常隔离怎么设计？
  • 分类处理：可重试错误（网络抖动、限流）用指数退避 + 抖动；不可重试错误（参数错、权限不足）直接回灌给模型换策略。
  • 超时设分级阈值，单个工具超时不拖垮整个任务；连续失败达到阈值熔断，避免死循环。
  • 把结构化错误信息（含错误码、建议）回灌给模型，而不是原始堆栈。
  • 必要时降级到备选工具或安全 fallback 回答。

主题 4 · 记忆管理与上下文工程

高频 Agent 的短期记忆和长期记忆如何实现、如何区分？
  • 短期记忆：当前会话的对话历史与工具结果，放在上下文窗口里；用滑动窗口 + 摘要压缩控制长度。存 Redis/内存，随会话结束释放。
  • 长期记忆：跨会话保留的信息——用户偏好（结构化 KV / JSON）、事实与经验（向量库）、任务结论。按需检索注入上下文。
  • 区分标准：按生命周期和更新频率——项目级规则几乎不变，放系统提示；用户偏好偶尔更新，外部 KV 按用户 ID 索引；会话上下文每次都变，放工作记忆。
  • 写入判断：不是所有对话都写，通常"用户明确偏好 / 关键事实 / 任务结论"才写，避免记忆污染。
加分答法：主动点出局限——当前主流记忆方案（向量存储、RAG、便签本、上下文管理）本质都是"备忘录"，是存取检索，不是把经验内化为权重的学习。这个区分能展示技术边界认知深度。
进阶 长期记忆和 RAG 有什么区别？
  • RAG：检索外部静态知识库（文档、资料），回答"知识是什么"。
  • 长期记忆：检索"关于这个用户/这段历史的动态信息"，回答"你是谁、我们聊过什么"。
  • 技术上都用向量检索，但数据来源、生命周期、写入策略不同。记忆约等于"持久化的、可检索的个人上下文"。
进阶 上下文压缩应该放在链路的哪一步？长对话窗口受限时滑动窗口 + 摘要怎么落地？
  • 时机：接近窗口阈值时触发，而不是每轮压缩；先压缩再向量化（避免把冗余信息也编码进去）。
  • 滑动窗口：保留最近 N 轮原文，早期对话逐步滚动出窗口。
  • 摘要：把滚出的内容用模型压成结构化摘要（关键事实、已完成任务、待办），摘要本身继续参与后续对话，并可再被压缩成"摘要的摘要"。
  • 工具结果压缩：大结果原地下采样/截断，或卸载到外部文件只保留引用，需要时再取回。
  • 避免突兀：异步分批压缩，别在用户等待时一次性大段压缩打断体验。
基础 什么是 Lost in the Middle？怎么缓解？
  • 模型对长上下文中部的信息利用率低，首尾信息更容易被注意到。
  • 缓解：重要信息放首尾；Rerank 把最相关内容放前面；压缩无关内容；检索结果少而精（Top-K 缩小到 3-5）。
高压 记忆有没有量化指标？怎么评测记忆对 Agent 效果的贡献？
  • 可以设计：记忆召回准确率（该记的有没有取回）、污染率（不该混的有没有混进来）、长任务目标达成率对比（开/关记忆的 A/B）、Token 节省量。
  • 用固定测试集 + 多轮对话脚本，对比开关记忆时的任务成功率。
加分答法：面试官爱问"提升百分比怎么算的"——提前想好你的测试集大小、基线是什么、统计口径是什么。

主题 5 · 多智能体协作与编排

进阶 多 Agent 相比单 Agent 的优势是什么？什么时候该拆？
  • 优势：分工专业化（不同角色用不同提示/工具）、并行执行提速、上下文隔离避免互相污染。
  • 代价：通信开销、错误传播、协调复杂度、成本上升。
  • 拆分时机：任务可清晰分解为相对独立的子任务；子任务需要不同工具/权限；单个上下文装不下所有信息。
  • 反直觉：多 Agent 不一定提升效率，很多场景一个强 Agent + 好工具更好——要能证明独特价值。
高压 多 Agent 调研系统是选中心化还是去中心化调度？怎么做到子任务失败可回退、进度可观测？
  • 中心化：主 Agent 规划并分发、回收结果。易控制、可观测、一致性强；但主 Agent 是瓶颈和能力上限。
  • 去中心化：Agent 间协商/广播，鲁棒但难调试、易不一致。
  • 调研类通常选中心化 + 可回退：主 Agent 持有任务图，每个子任务有状态（待办/进行/成功/失败），失败触发重试或替代路径，不阻塞全局。
  • 可观测：每个子任务有独立 ID 和 Trace，进度汇总到看板；关键中间结果落盘，便于回放。
加分答法：提"断点恢复"——子任务状态持久化，失败后从失败节点继续，而不是从头重跑。
进阶 多个 Agent 如何做到完全隔离（上下文、权限、存储）？
  • 上下文隔离：每个子 Agent 独立 messages，只接收主 Agent 传入的必要信息，不共享全量历史。
  • 权限隔离：按 Agent 角色配置可访问的 MCP 服务和工具白名单——不是所有 Agent 都能访问全部 MCP。
  • 存储隔离：独立 namespace / 数据库 schema，跨 Agent 通信走明确定义的消息格式（JSON / Markdown 任务卡）。
进阶 主 Agent 怎么知道子 Agent 执行完成？多个 Agent 结论不一致怎么处理？
  • 完成检测：显式完成消息 + 状态字段；异步场景用回调/消息队列；超时未完成按失败处理。
  • 结论冲突：交给主 Agent 裁决（带各方证据）；或引入评审 Agent；或按置信度/来源可信度加权；无法裁决时升级人工。
进阶 Agent Team 和动态任务分发机制了解吗？除了路由分发还有哪些协作方式？
  • 常见模式：路由分发（按任务类型选专家）、流水线（上下游串联）、并行汇总（多 Agent 独立产出后合并）、辩论/评审（多视角对抗提升质量）、层级团队（主管 + 执行者）。
  • 动态分发：主 Agent 根据任务内容和各子 Agent 能力/负载实时决定分给谁，而非写死。

主题 6 · 评估、幻觉与安全兜底

高频 Agent 死循环 / 无限调用的原因及解决方案？为什么要三层防护？
  • 原因：Prompt 逻辑闭环、工具持续报错、模型没收到有效反馈、目标无法达成又不会退出。
  • 三层防护：① 硬限制——最大步数、超时；② 检测——重复动作检测（相同工具+参数哈希）、无进展计数；③ 逃生——Prompt 内置失败退出策略 + 观察者 Agent 强制介入。
  • 为什么要三层：只靠最大轮次太粗暴（误杀合法长任务），必须有语义级的"无进展"判断；多层兜底避免单点失效。
高频 生产环境 Agent 的四类典型故障怎么发生、怎么解决？
故障成因对策
思考链错误传播早期步骤判断错误，后续全盘皆错每步目标对齐、定期反思重规划、关键节点校验
工具幻觉调不存在的工具 / 编造参数工具名白名单、Schema 校验、检索式工具选择
JSON 格式崩坏长上下文下指令遵循退化结构化输出约束、格式校验 + 回灌修正
无限循环见上题三层防护
加分答法：再补一个"上下文污染"——工具返回超大/无关内容把上下文带偏，对策是截断 + 任务重置 + 必要时新开 session。
高频 如何量化评估 Agent 的"幻觉率"？如何构建评测体系？
  • 定义口径：幻觉率 = 无事实依据的断言数 / 总断言数。先要有 Golden Dataset（标准问答 + 事实标注）。
  • 判定方法：① 用更强的模型做 LLM-as-a-Judge（要校验它自身的一致性）；② 用工具返回的实际结果比对 Agent 声称的结果；③ 多裁判投票降低单裁判偏差。
  • 评测维度：结果正确性 + 轨迹质量（步骤是否合理、工具是否选对）+ 效率（步数、Token、成本）+ 安全性（越权、注入）。
  • 区分："内容过时" ≠ "幻觉"——前者是知识时效问题（用 RAG 更新），后者是无中生有。
必被追问：如果检测 Agent 自身也会幻觉，怎么保证它可靠？——答：多裁判交叉验证 + 用可验证的工具结果做锚点 + 定期用人工标注校准裁判。
高频 Prompt Injection / 间接注入是什么？如何防范？
  • 直接注入：用户直接说"忽略之前所有指令"。间接注入：恶意指令藏在网页、外部文档里，Agent 抓取后被带偏。
  • 防范：① 数据与指令分离——外部内容明确标记为"不可信数据"，系统指令优先级最高；② 输入过滤与白名单；③ 工具权限最小化；④ 高危操作人工确认（HITL）；⑤ 沙箱执行；⑥ 输出审核；⑦ 连续认证（不只初始认证）。
加分答法：强调"最小权限 + 人在回路"是最后防线——不要指望靠提示词防住所有注入。
进阶 如何建立 Agent 的可观测性？线上 Agent 一直调工具不返回怎么 Debug？
  • 三件套：轨迹留存（每步 Thought/Action/Observation）、指标（成功率、步数、Token/成本、工具错误率、幻觉率）、回放（按 trace_id 重现执行）。
  • 全链路 Trace：串联模型调用、检索、工具执行，定位耗时和失败点。
  • Debug：分段看 trace——模型有没有发出 tool_call？工具有没有返回？结果有没有正确回灌？逐步排除是 Prompt、模型、工具还是逻辑问题。
进阶 HITL 触发人工确认时 Agent Loop 处于什么状态？怎么暂停、暂存和恢复？
  • Loop 进入"等待态"：当前节点执行到高危操作前挂起，不继续往下。
  • 状态暂存：把 State（消息、进度、待确认操作）连同 thread_id 写入 checkpoint。
  • 恢复：审批通过后，从 checkpoint 恢复，把"已批准/已拒绝"作为一条观察注入，继续执行或走拒绝分支。
  • 配合超时：人工长时间不响应要有超时兜底（默认拒绝/升级通知）。

高频 设计一个企业级 Agent 系统 / AI 面试官 Agent，怎么搭架构？

五层架构（画出来就是加分项）：

层职责

追问必答五点：

  • 记忆设计：Redis 短期 + 向量库长期
  • 可靠性：超时 + 熔断 + 人工审批
  • 可观测：Trace + 成本监控
  • 安全：注入防御 + 最小权限 + 数据脱敏
答法模板：先问清场景和约束（用户量、延迟、成本、合规）→ 画分层架构 → 逐层展开关键设计 → 主动讲 trade-off 和风险兜底 → 给量化指标。切忌上来就直接画。
进阶 Agent 项目最大的瓶颈是什么？如何控制 Agent 调用成本？
  • 最大瓶颈：可靠性和成本——不是做不出来，是算不过账、跑不稳。Anthropic 都说"能用 Workflow 就别上 Agent"。
  • 降本：模型分级路由（简单任务用小模型，复杂才升级）；缓存重复结果；上下文压缩减少 Token；限制反思轮次；流式/批处理；设预算上限；监控每次任务成本。
进阶 模型路由：三种能力/价格不同的模型，怎么自动选择并在不可靠时升级？
  • 按任务复杂度分级：分类/抽取等简单任务走小模型，长文档分析/复杂推理走大模型。
  • 用置信度或自检结果判断可靠性，低置信升级到更强模型或触发人工。
  • 成本/延迟作为路由约束，设熔断阈值。

主题 8 · 手撕代码

手撕 手写一个 ReAct Agent 的核心循环（含防死循环） 
def react_loop(llm, tools, user_input, max_steps=6):
    messages = [system_msg, user_msg]
    seen = set()                # 重复动作检测
    for step in range(max_steps):
        resp = llm(messages, tools=tools)
        if not resp.tool_calls:     # 没有工具调用 → 最终答案
            return resp.content
        messages.append(resp)        # 先放 assistant 的 tool_calls
        for call in resp.tool_calls:
            args = json.loads(call.function.arguments)
            sig = (call.function.name, json.dumps(args, sort_keys=True))
            if sig in seen:            # 第二层：重复检测
                content = "错误：重复调用，请换方式或给结论"
            else:
                seen.add(sig)
                content = tools[call.function.name](**args)  # 执行
            messages.append({"role":"tool",
                             "tool_call_id":call.id, "content":content})
    return "达到最大步数，请人工介入"   # 第一层：硬限制

要点：assistant 的 tool_calls 消息必须在对应 tool 消息之前；错误当观察回灌；至少两层防护。第 1 课有可运行的完整版本。

手撕 RAG 的 chunk 策略、混合检索、rerank 怎么实现？
  • 分块：按语义边界——代码按函数、Markdown 按标题层级、PDF 按段落；Chunk Size 256-512 token，重叠 10-20%，防关键信息被切断。
  • 混合检索：BM25（关键词精确匹配）+ 向量检索（语义相似）融合，取长补短。
  • Rerank：用 Cross-Encoder 对召回的 Top-20~50 重排序，取 Top-3~5 喂给 LLM——向量检索 Recall 高但 Precision 有限，重排降噪又省 Token。
  • 评估：检索阶段看 Recall@K / MRR；生成阶段看答案正确率、忠实度（是否基于检索内容）。

主题 9 · LLM 基础认知

基础 上下文窗口是什么？Temperature / Top-P / Top-K 有什么区别？怎么调？
  • 上下文窗口：模型单次能处理的 Token 上限（输入 + 输出），超出会截断或遗忘中部内容（Lost in the Middle）。
  • Temperature：缩放 logits 改变分布陡峭度——越低越确定，越高越随机。
  • Top-K：只保留概率最高的 K 个候选；Top-P（nucleus）：保留累计概率达 P 的最小候选集，动态调整数量。
  • 实践：Agent 场景通常低温（0~0.3）保证稳定；创意场景调高。别同时乱调多个参数。
基础 模型幻觉怎么产生？Agent 场景怎么缓解？
  • 成因：预训练知识边界 + 概率生成机制——模型"补全"未知内容而非查询事实。
  • 缓解：RAG 提供事实依据、工具返回真实数据、要求引用来源、结构化输出约束、LLM-as-Judge 校验、不确定时让模型说"不知道"。
基础 Transformer 架构和注意力机制的基本原理？
  • 自注意力让每个 Token 计算与其他 Token 的相关性（Query/Key/Value），从而建模长距离依赖；多头注意力从不同子空间捕捉关系。
  • 位置编码弥补注意力本身无顺序信息的问题。Decoder-only 架构通过因果掩码实现自回归生成。
  • 面试不用推公式，说清"为什么注意力能建模上下文、为什么有窗口限制"即可。

第 1 课 · 手写你的第一个 ReAct Agent

① 概念：Agent 到底是什么

剥掉所有花哨包装，一个 Agent 就是一个循环：

1
Thought（思考）：LLM 看当前情况，决定下一步做什么。
2
Action（行动）：输出一个结构化的工具调用（函数名 + 参数）。注意——模型只"说要调用"，真正执行的是你的代码。
3
Observation（观察）：你的代码执行工具，把结果写回对话历史。
4
回到 1，直到模型不再调用工具，给出最终答案，或触发终止条件。

记住这个等式：Agent = LLM（大脑）+ Loop（循环）+ Tools（手脚）+ State（记忆）。后面所有复杂概念都是在这四块上加东西。

② 代码：可运行的最小实现

import json
from openai import OpenAI   # 可换成任意兼容接口

client = OpenAI()  # 配置好 base_url / api_key

# 1. 用 JSON Schema 描述工具（模型据此决定调哪个、传什么参数）
TOOLS = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市的当前天气",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名，如 北京"}
            },
            "required": ["city"]
        }
    }
}]

# 2. 真正被执行的函数
def get_weather(city: str) -> str:
    return f"{city}今天晴，26℃"   # 真实场景这里调天气 API

TOOL_MAP = {"get_weather": get_weather}

SYSTEM = """你是一个助手。需要外部信息时调用工具，不要编造。
拿到工具结果后继续推理，能回答时直接给出答案。"""

def react_loop(user_input: str, max_steps: int = 6):
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user", "content": user_input}]
    seen = set()   # 重复动作检测

    for step in range(max_steps):
        resp = client.chat.completions.create(
            model="gpt-4o-mini", messages=messages,
            tools=TOOLS, tool_choice="auto").choices[0].message

        if not resp.tool_calls:          # 情况 A：最终答案
            return resp.content

        messages.append(resp)           # 情况 B：先放 assistant 的 tool_calls
        for call in resp.tool_calls:
            args = json.loads(call.function.arguments)
            sig = (call.function.name, json.dumps(args, sort_keys=True))
            if sig in seen:               # 防死循环：重复检测
                content = "错误：重复调用，请换方式或直接给结论"
            else:
                seen.add(sig)
                content = TOOL_MAP[call.function.name](**args)  # 执行真实函数
            messages.append({"role": "tool",
                             "tool_call_id": call.id, "content": content})
    return "达到最大步数，请人工介入"      # 防死循环：硬限制

print(react_loop("北京今天天气怎么样？"))

③ 验证：怎么确认你真的懂了

验证 1 · 跑通：执行后应输出天气答案。打印每轮的 messages，观察 Thought → tool_call → tool 结果的完整流转。
验证 2 · 理解工具描述的作用：把 description 改成模糊的"查东西"，看模型是否开始选错或编造。
验证 3 · 错误当反馈：让 get_weather 故意抛错，把错误字符串回灌，看模型会不会换策略——这就是"错误是观察而非异常"。
验证 4 · 死循环防护：把 max_steps 设成 2，观察"达到最大步数"分支被触发。
本课作业：① 再加一个工具（如计算器），让模型在两个工具间选择；② 给 seen 检测加打印日志，证明重复调用被拦住；③ 用一段话回答面试题"ReAct 原理及优缺点"——你会发现写的代码就是答案。
